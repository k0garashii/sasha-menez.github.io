    Gameplay en C++

    Scripting & Hot Reload

    Je voulais retrouver le confort d'Unreal : écrire un script de gameplay en C++, cliquer sur Hot-Reload, et voir ses variables apparaître dans l'inspecteur sans relancer l'éditeur ni perdre la scène.

    • C++20
    • DLL
    • RTTR
    • CMake
    • Code generation

    Côté utilisateur

    Écrire un script

    Un script hérite de Script<T> et marque ses variables éditables avec ENIGMA_PROPERTY(). C'est tout : pas de fonction d'enregistrement à écrire à la main.

    class Test : public Script<Test>
{
    ENIGMA_CLASS(Test)
public:
    ENIGMA_PROPERTY()
    float speed = 5.0f;
};

    Le ScriptManager appelle ensuite le cycle de vie classique d'un moteur de jeu : Awake, Start, Update, FixedUpdate (au rythme de la physique), LateUpdate et End, plus OnCollisionEnter / Stay / Exit venant de la couche physique. Les scripts sont rangés dans une liste par étape, et l'éditeur peut générer un nouveau script à partir d'un modèle.

    Génération de code

    Une réflexion générée automatiquement

    L'inspecteur du moteur repose sur RTTR : il n'affiche que ce qui est enregistré dans la réflexion. Plutôt que de demander à l'utilisateur d'écrire ces enregistrements, le moteur les génère :

    1. Lecture des headersLe dossier de scripts est parcouru à la recherche de ENIGMA_CLASS et ENIGMA_PROPERTY.
    2. properties.jsonClasses, types et valeurs par défaut sont écrits dans un fichier intermédiaire.
    3. generated_reflection.cppUn fichier C++ enregistre chaque classe dans RTTR avec les métadonnées d'UI de l'inspecteur.
    4. Points d'entrée exportésEnigmaRegisterScriptReflection et Unregister sont exportés par la DLL.

    Le type C++ choisit le widget : un float devient un champ glissant, un bool une case à cocher, un Vector3D trois champs, un GameObject* une référence d'objet. Chaque script est aussi ajouté à la liste des composants de l'éditeur, avec son icône.

    Le cœur du système

    Le pipeline de hot reload

    Le rechargement est une vraie chaîne de production, lancée dans une tâche asynchrone pour ne pas bloquer l'éditeur pendant la compilation :

    1. DéchargementLes scripts sont désinscrits, leur réflexion et leurs caches d'inspecteur effacés.
    2. GénérationJSON puis generated_reflection.cpp.
    3. Compilationcmake --fresh puis cmake --build sur le projet de scripts, sortie dans build_log.txt.
    4. PromotionLa DLL et le PDB les plus récents sont copiés à l'emplacement attendu.
    5. ChargementCopie versionnée script_reloaded_N.dll, puis LoadLibrary et enregistrement de la réflexion.
    6. RéattacheLes scripts et leurs valeurs sont recollés aux bons objets de la scène grâce à leur UUID.
    auto AsyncHotReload = []()
{
    UnloadScripts();
    LibLoader::WriteInJson();
    LibLoader::CreateCppFromJson();
    if (!LibLoader::CompileScript()) return;
    if (!LibLoader::LoadScriptDLL())  return;
    Serializer::GetInstance().AttachedScript(SceneManager::GetInstance().GetCurrentScene());
};
Async::GetInstance().CreateTask(AsyncHotReload);

    Ce qui a résisté

    Problèmes résolus

    DLL verrouillée

    Windows verrouille une DLL chargée : impossible de la réécrire pendant que l'éditeur tourne. Le moteur charge donc une copie numérotée, et la DLL d'origine reste libre pour la compilation suivante.

    Réflexion périmée

    Sans précaution, RTTR garderait des types pointant vers le code de l'ancienne DLL. Chaque DLL exporte donc sa propre fonction de désinscription, appelée avant le FreeLibrary.

    Garder la scène

    Les objets ne sont pas recréés : seuls les scripts sont détachés puis réattachés, avec les valeurs de leurs propriétés sauvegardées dans le fichier de scripts de la scène.

    Les erreurs de compilation ne font jamais tomber l'éditeur : chaque étape renvoie un échec propre, journalisé dans la console du moteur, et le log de build complet reste disponible.

    Limites et suite

    Un parseur volontairement simple

    La lecture des headers est ligne à ligne : une propriété doit tenir sur la ligne qui suit sa macro. Un vrai parseur (ou libclang) rendrait le système plus robuste.

    Plus de types exposés

    Les propriétés couvrent aujourd'hui float, int, bool, Vector3D et GameObject*. Les tableaux, les enums et les références d'assets sont les prochains types à ajouter.
